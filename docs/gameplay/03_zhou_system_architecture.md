# 周盟系统技术架构

## 文档定位

本文为EU4 1.37.*下“自写中华体系”的技术设计。目标是在不删除欧洲神圣罗马帝国的前提下，用EU4脚本原语实现一个功能和体验近似神罗、政治逻辑属于周盟的独立系统。

本文描述的是架构与可行性判断。当前原型已经加入天子与成员名册、全局天子事件
目标、开局总览、版图高亮、-100—100礼乐值、0—100盟功、五档秩序修正、年度礼乐演算、
开封大朝会、一项盟约改革、一条低礼统天下事变和可拖拽专属GUI初版。旧版两套
自定义封邦属国已经移除；方伯选举、共同防御、非法领土和完整改革树仍未实现，
专属GUI仍需继续打磨布局与交互。

## 核心结论

### 已确认的技术边界

- EU4不能通过普通模组脚本注册第三个原生 `empire` 对象。
- 欧洲神罗的选举、成员列表、地图模式和部分战争行为包含硬编码，不能原样复制为第二套系统。
- 自写体系只能追求玩法功能相似，不能让引擎内部与神罗完全同构。

### 推荐实现方向

- 不把欧洲神圣罗马帝国迁移到中国，也不删除欧洲神罗。
- 周盟使用变量、旗标、事件、决议、战争借口、修正和自定义界面组合实现。

### 推荐总体结构

周盟采用“双元核心＋独立成员模型”：

- 周天子固定世袭，负责法统、册封、礼统和盟约；
- 方伯通过诸侯推举产生，负责共同防御与军事执行；
- 诸侯在引擎中保持独立或维持各自原有直属关系，周天下身份由旗标另行记录；
- 成员身份、特殊席位、盟功和违约状态同时使用旗标与变量记录；
- 欧洲神罗和原版中华帝国机制不承担周盟的日常运行。

原版中华帝国可以保留为一种待定终局：某国废除周盟、完成问鼎后，才转入中央集权的天命体系。这不是MVP依赖项。

## 为什么不直接复制神罗

EU4原版神罗的皇帝、选帝侯、帝国成员、帝国权威、改革和部分战争规则具有硬编码行为。原版文件可以修改 `empire = hre` 的改革，却不能用普通脚本创建一个并行的 `empire = zhou`。

直接把神罗改到中国会带来以下代价：

- 欧洲数百个省份的 `hre = yes` 历史必须重写；
- 欧洲选帝侯、皇帝和改革链被占用；
- 大量原版事件、任务、AI行为与成就可能错误触发；
- 与欧洲地图、历史和大型模组严重冲突；
- 最终仍无法同时保留两个独立的原生神罗容器。

因此，自定义状态机是本项目的推荐路线。

## 功能可行性矩阵

| 神罗式功能 | 周盟实现 | 可行度 | 主要限制 |
|---|---|---:|---|
| 固定政治中心 | 周国作为系统锚点，开封作为王畿中心 | 高 | 必须防止周国被普通吞并或随意换标签 |
| 帝国成员 | `zhx_member` 国家旗标 | 高 | 成员身份本身不改变国家的原生外交关系 |
| 成员互战、结盟、联姻 | 使用独立国家的原生外交规则 | 高 | 盟约禁战或制裁需要事件与战争借口补充 |
| 不占天子外交槽 | 成员不是天子的直属属国 | 高 | 原有普通附庸仍按其自身关系占槽 |
| 帝国权威 | 周国变量 `zhx_ritual_authority`，限制在-100—100 | 高 | 没有原生顶栏与自动提示 |
| 皇帝 | 世袭周天子 | 高 | 继承危机和周国灭亡必须自写 |
| 选帝侯 | 五或七个“议政诸侯”旗标 | 高 | 席位数量与产生办法尚未确定 |
| 皇帝选举 | 改为方伯推举 | 高 | 投票由事件和AI权重模拟，不是原生选举 |
| 帝国改革 | 盟约旗标、决议和表决事件 | 高 | 自定义界面与AI评估需单独编写 |
| 帝国事变 | “天下事变”事件状态机 | 高 | 复杂事变必须防止事件重复与卡死 |
| 皇帝保护成员 | 周室召集、方伯干预、反侵略战争借口 | 中 | 原生自动参战无法直接照搬，战争边界需原型验证 |
| 非法领土 | 记录成员省份易手，触发归还或复国要求 | 中 | 和谈、附庸吞并、叛军和事件转让有很多例外 |
| 自由市 | 礼邑、通商公邑旗标与修正 | 高 | 保护义务和数量上限由脚本维护 |
| 宗教联盟战争 | 思想阵营、盟约危机与特殊战争 | 中 | 无法直接获得原生联盟战争的全部外交逻辑 |
| 解散神罗 | 占领开封、击败关键成员后执行“废盟／问鼎” | 高 | 必须清除成员旗标、席位和盟约状态 |
| 联邦化终局 | 盟约改革、成员授权和统一标签 | 高 | 吞并、继承核心和AI接受度需平衡 |
| 专属界面 | 自定义GUI显示天子、方伯、礼统、席位和改革 | 中高 | 动态国家列表、输入与刷新必须实机原型 |
| 独立顶栏按钮 | 覆盖或扩展顶栏界面 | 中 | 易与其他界面模组冲突，不建议MVP采用 |
| 专属地图模式 | 无法注册真正等价的原生新地图模式 | 低 | 可用高亮、决议或界面列表近似 |
| 多人游戏一致性 | 事件、变量与固定排序 | 中 | 玩家同时投票、暂停和事件目标需专项测试 |

## 系统分层

### 一、数据层

数据层定义稳定的国家、身份和规则词汇：

- 周国标签与王畿；
- 周天下成员名册；
- 成员、议政诸侯、礼邑、通商公邑、方伯等旗标；
- 盟约改革旗标；
- 礼统、盟功、违约和任期变量；
- 与系统配套的修正、战争借口与本地化。

跨诸夏内容统一使用 `zhx_` 前缀；广东独有内容继续使用 `gdd_`。

### 二、状态层

推荐由周国充当持久化数据锚点。这样可以通过周国作用域保存全局状态；成员身份以
各国的 `zhx_member` 旗标为权威真源，只有初始化、名册修复或制度性变更时才重新枚举，
不使用每日或每月的全世界循环。

周国需要以下保护：

- 不能被普通外交吞并；
- 失去开封不等于立刻删除国家；
- 周盟解散时先完成状态清理，再允许周国灭亡或转型；
- 标签切换、被附庸和被迫迁都都要有明确规则。

如果后续发现周国作为数据锚点过于脆弱，可以考虑隐藏系统国，但这会增加地图外国家、外交和存档问题，不作为首选。

### 三、规则层

规则层通过脚本触发器与效果统一处理：

- 是否为周盟成员；
- 是否有资格成为议政诸侯或方伯；
- 礼统与盟功增减；
- 诸侯被灭是否构成“绝其社稷”；
- 外敌战争是否触发共同防御；
- 盟约改革是否可提案、表决和执行；
- 问鼎、废盟与联邦化的前置条件。

重复逻辑应放入 `scripted_triggers` 和 `scripted_effects`，避免每个事件各写一套标准。

### 四、事件层

事件层负责不能依靠原生外交AI稳定完成的行为：

- 开封朝会；
- 议政诸侯投票；
- 方伯候选与推举；
- 秦国请求援助；
- 周室、方伯和普通诸侯响应外敌；
- 非法吞并后的归还、复国或拒命；
- 改革表决；
- 周室继承危机；
- 问鼎与周盟解散。

### 五、呈现层

MVP先使用决议、事件、国家修正和触发式提示呈现信息。系统稳定后再制作“诸夏会盟”界面，显示：

- 周天子、王朝和王畿；
- 当前礼统；
- 当前方伯、任期和支持者；
- 议政诸侯；
- 正在处理的天下事变；
- 盟约改革；
- 玩家盟功、违约和投票状态。

不建议MVP覆盖顶栏。顶栏按钮应当在玩法稳定、界面兼容策略确定后再做。

## 成员模型

### 独立政治成员

周天下成员不是一类自定义属国。`zhx_member` 只表示国家属于天下秩序，不负责改变
其直属外交关系：独立国家仍是独立国家，楚的普通附庸仍以楚为宗主，同时也可以拥有
周天下成员身份。这使成员之间沿用正常军事通行、宣战、结盟和联姻规则，也避开了
“同一宗主的属国自动互相通行”这一硬编码限制。

贡赋、勤王、共同防御、非法吞并和拒命以后由周盟规则层分别处理，而不是借用自由欲、
属国税或宗主战争自动参战。成员进入、退出与天子更替必须调用统一脚本效果，使旗标、
成员计数和界面缓存保持同步。

### 旗标与特殊身份

建议成员国使用以下工作旗标：

| 旗标 | 含义 |
|---|---|
| `zhx_member` | 正式周天下成员 |
| `zhx_council_seat` | 议政诸侯 |
| `zhx_fangbo` | 当前方伯 |
| `zhx_ritual_state` | 礼邑 |
| `zhx_free_city` | 通商公邑 |
| `zhx_under_interdict` | 受到绝祀、削爵或盟约制裁 |
| `zhx_refused_muster` | 最近一次共同防御中拒绝义务 |
| `zhx_overseas_seat` | 获准参加会盟的海外封国 |

旗标名称是工作设计，实际实现前仍需统一审计。

## 变量模型

### 周国变量

| 变量 | 建议范围 | 用途 |
|---|---:|---|
| `zhx_ritual_authority` | -100—100 | 周室法统与天下秩序，即“礼乐值” |
| `zhx_reform_stage` | 整数 | 缓存当前改革进度，正式权威仍以改革旗标为准 |
| `zhx_member_count_cache` | 非负整数 | 界面和周期计算使用的成员数缓存 |
| `zhx_crisis_state` | 枚举整数 | 当前天下事变阶段 |
| `zhx_fangbo_term_end` | 年份或日期编码 | 判断是否需要重新推举 |
| `zhx_destroyed_members` | 非负整数 | 记录未复国的正式成员数量 |

### 成员国变量

| 变量 | 建议范围 | 用途 |
|---|---:|---|
| `zhx_merit` | 0—100 | 盟功；衡量勤王、军饷、难民安置和盟约执行 |
| `zhx_compliance` | 0—100 | 对共同义务的履行程度 |
| `zhx_treaty_breaches` | 非负整数 | 拒命、非法吞并和破坏朝会的累计记录 |
| `zhx_fangbo_score_cache` | 非负数 | 方伯候选评分缓存 |
| `zhx_vote_weight_cache` | 非负数 | 议政席位在特定表决中的权重 |

所有有界变量必须通过统一效果修改并钳制范围：礼乐值为-100—100，盟功与履约度为0—100；禁止事件直接任意加减而越界。

### 礼统来源与损失

原型已经把礼统权威值保存在天子国家，并通过年度脉冲进行低频更新。天子的稳定、
威望与战争状态提供基础变化，成员的稳定和战争状态提供小额合计变化；朝会、成员奉礼、
盟约改革和天下事变则产生离散变化。所有入口在写入后钳制到 `-100—100`。

为避免每月给全图国家重挂修正，原型只在礼统跨越 `20/40/60/80` 边界时重建成员
修正。五档依次为“礼崩乐坏”“礼教废弛”“礼乐相持”“礼制稳固”和“纲常有序”。
高礼统提高税收与生产、同时提高侵略扩张；低礼统提高训练度，并损害收益、安定或
荒废度。这是连续礼统值的分档玩法近似，不是原生进度条。

以下数值只作为平衡占位，不是最终参数。

可增加礼统的行为：

- 成功保卫遭外敌进攻的成员；
- 诸侯响应共同军饷或出兵；
- 通过盟约仲裁而非战争解决成员争端；
- 恢复被非法吞并的礼邑或成员国；
- 举行开封朝会并完成有效表决。

可降低礼统的行为：

- 开封或洛阳周室宗庙被占领；
- 方伯拒绝交还临时权力；
- 成员被吞并而周室无力处置；
- 大量诸侯拒绝共同防御；
- 周天子破坏盟约、偏袒单一国家或册封失信；
- 天下事变超时或进入无结果状态。

## 方伯推举

### 候选资格

推荐要求候选国：

- 是正式周盟成员；
- 未受盟约制裁；
- 不是礼邑或通商公邑；
- 拥有最低发展度、军力或盟功；
- 当前没有公开问鼎或废盟；
- 在共同防御中没有尚未结算的拒命记录。

### 议政诸侯

议政席位推荐为五席或七席，最终数量待定。席位来源可以混合：

- 固定礼制席：例如周室指定的鲁；
- 区域席：北方、东方、南方、西方各一；
- 盟功席：周期内盟功最高者；
- 海道席：当海外体系发展后授予。

为了MVP可控，第一版宜使用固定标签名单和简单替补规则，后续再改为完全动态。

### 投票流程

1. 任期结束、方伯死亡、被废黜或重大危机触发推举；
2. 系统筛选候选并计算基础评分；
3. 玩家控制的议政诸侯收到投票事件；
4. AI根据关系、盟功、军力、共同敌人、文化接近和改革立场加权选择；
5. 平票由周天子裁决；
6. 胜者获得方伯旗标、任期和共同防御权限；
7. 旧方伯拒绝交权时可触发霸府危机。

EU4没有可直接复用的第二套原生选帝界面，因此选票记录建议先采用有限候选旗标。完全动态候选列表和界面属于后期研发项。

## 盟约改革

### MVP改革

首个可玩版本只需三项盟约：

1. **定开封常会**：固定朝会周期，开放议政与盟功机制；
2. **立列国籍簿**：明确正式成员、复国义务与非法吞并惩罚；
3. **订共御之约**：建立外敌入侵时的军饷、出兵和方伯权限。

### 后续分支

推荐把完整改革树分成三条，而不是简单线性中央集权：

- **尊王线**：增强周室财政、仲裁与直接保护权；
- **霸府线**：强化方伯、常备联军和战时征发；
- **公约线**：强化议政席位、成员平等和联邦共同机构。

三条路线可以在终局分别导向王权复兴、霸主统一或列国联邦。是否允许混合改革待定。

## 天下事变架构

### 通用状态机

每场天下事变至少包含：

1. **发现**：满足条件并确认没有其他互斥事变；
2. **提案**：周室、方伯或成员提出议题；
3. **表态**：议政诸侯与相关国家选择立场；
4. **执行**：生成军饷、修正、战争、仲裁或期限；
5. **结算**：调整礼统、盟功、关系和改革进度；
6. **清理**：删除临时旗标、事件目标和缓存，允许下一场事变。

每一阶段都要有超时兜底，避免统治者死亡、国家灭亡或战争提前结束导致系统永久卡住。

### 斡罗斯危机

推荐作为第一场教学事变：

1. 秦使请求开封大朝会；
2. 各国选择出兵、军饷、难民安置或拒绝；
3. 诸侯根据贡献积累盟功；
4. 需要时提前推举战时方伯；
5. 停战结束后由秦、方伯或周室决定共同战争；
6. 根据收复河西、守住关中、议和或惨败分别结算；
7. 斡罗斯可以被驱逐、被承认为河西国家、接受周册或继续扩张。

## 共同防御与非法领土

### 共同防御

这是最高风险的核心功能。原版朝贡国关系并不自动提供完整的神罗皇帝护成员体验。推荐准备两层方案：

- 首选：外敌攻击成员后，通过事件邀请周室、方伯和承诺出兵的诸侯加入防御；
- 兜底：若直接加入既有战争不稳定，则生成“救援成员”的并行特殊战争或战争借口。

必须测试外敌宣战、成员主动挑衅、共同敌人、已有联盟、摄政、联统、附庸链和多人游戏等边界。

### 非法领土

成员省份易手后，系统判断：

- 领土是否属于被灭的正式成员；
- 转让是否来自合法仲裁、继承或改革；
- 新所有者是否为周盟成员；
- 周室与方伯是否有能力要求归还；
- 拒绝后是制裁、复国战争还是直接降低礼统。

不能只依赖一种战争结束钩子。事件转让、叛军独立、外交吞并和任务效果都可能改变所有权，需要在低频校验中补漏。

## 事件与文件命名建议

| 命名空间 | 职责 |
|---|---|
| `zhx_core` | 初始化、成员缓存、系统修复和调试 |

## 性能策略

- 优先在开局、君主更替、战争变化、事变和改革时更新。
- 不每月遍历全球所有国家与省份。
- 成员计算优先从周国维护的事件目标槽或成员缓存开始。
- 季度或年度校验只负责修复漏掉的状态，不承担所有核心逻辑。
- GUI读取缓存变量，避免每次刷新重新计算复杂条件。
- 调试版可以提供人工“修复周盟状态”决议，正式版隐藏。

## 兼容与测试风险

### DLC

自定义系统不应把是否拥有某一DLC作为唯一运行条件。涉及天命、政府改革、统治者特性或特殊界面的内容要分别在常见DLC组合下测试，并提供缺少DLC时的降级路径。

### 存档

全国开局历史、标签和成员结构发生变化后，旧版广东存档原则上不兼容。新系统必须测试：

- 保存并读取后变量与旗标是否保留；
- 方伯任期是否重复触发；
- 事变中途读档是否能够继续；
- 周国灭亡、释放和重建后系统是否能恢复。

### AI

AI不会天然理解“盟功”“礼统”或自定义方伯。所有关键选择都要提供可解释的AI权重，且至少覆盖：

- 自身安全；
- 与秦、周、方伯和斡罗斯的关系；
- 当前债务、人力与战争；
- 政治路线和统治者性格；
- 玩家是否正在利用重复事件刷取收益。

### 界面

界面层不应反向决定规则层。即使专属GUI暂时失效，玩家也应该能通过决议、事件和修正查看并操作核心系统。

## MVP验收标准

周盟系统原型至少满足以下条件，才可称为“可玩”：

1. 周国与五个测试成员能在1444年正确初始化；
2. 成员不占周国外交槽，不能被普通外交吞并；
3. 成员可以按预期互相外交和战争；
4. 礼统与盟功能增减、钳制、存档并读取；
5. 议政诸侯能够完成一次方伯推举；
6. 三项MVP盟约能够提案、表决、生效并显示；
7. 外敌攻击成员时共同防御至少有一种可靠执行路径；
8. 斡罗斯事变可以进入至少三种不同结局；
9. 国家灭亡、统治者死亡或中途读档不会永久卡住状态机；
10. 欧洲神罗仍能正常运作；
11. 没有专属GUI时，全部核心信息仍然可见；
12. 连续观察若干十年时，周期脚本没有明显性能问题。
