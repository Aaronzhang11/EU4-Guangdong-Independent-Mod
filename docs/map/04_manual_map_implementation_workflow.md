# EU4 手绘拆省与正式实装标准流程

## 文档目的

本文把 B01 广东地图的实践整理为可复用的标准作业流程。它适用于《列国奉周》
后续所有拆省批次，也可作为其他 EU4 1.37.5 地图模组的实施参考。

流程的目标不是“成功画出一种新颜色”，而是交付一个能够被 EU4 加载、能够点击、
拥有完整历史和经济数据、可以保存读取，并且不会在下次构建时被自动化工具覆盖的
正式省份。

配套的可复制表单见
[拆省批次实施与验收模板](templates/province_split_batch_template.md)。

## 一、核心原则

### 1. 正式 BMP 是唯一几何源

正式边界只存在于模组的：

`map/provinces.bmp`

审图 PNG、AI 草图、矢量轮廓、坐标列表和 staging BMP 都只能作为参考。正式
构建器可以读取、审计和记录 `provinces.bmp`，但不得生成、复制或覆盖其像素。

如果玩家重新手绘了边界，自动化检查失败是正常的安全提示。正确处理方式是审查
新边界并更新断言、点位和联动资产，而不是用旧生成器“修复”正式图。

### 2. 几何母省与数值母省可以不同

手绘时可能需要跨越原版多个省份，才能获得合理的现实地理轮廓。此时必须分别记录：

- **几何来源**：新颜色实际替换了哪些原版或已有省份的像素；
- **数值母省**：发展度、商品、核心和历史主要从哪个省份体系拆分；
- **政治归属**：1444 年所有者、核心和争议关系。

三者不必机械一致，但差异必须写入总表和审图记录。

### 3. 一次只改变一个主要变量

建议按以下顺序推进：

1. 冻结省份名单、ID 和 RGB；
2. 手绘边界；
3. 审核几何与点位；
4. 分配发展度、商品和历史；
5. 生成配套文本资产；
6. 静态验证；
7. 引擎实机验证。

不要同时大改海岸线、国家边界、发展度和系统机制。否则出现问题时很难判断错误
来自哪一层。

### 4. 静态通过不等于实机通过

脚本可以证明格式、颜色、邻接、点位和数据关系自洽，但不能替代 EU4 引擎。
任何新地图批次必须以全新 1444 年存档完成最终验收。

## 二、权威资产与职责分工

| 资产 | 职责 | 是否手工维护 |
|---|---|---|
| `map/provinces.bmp` | 唯一正式省界与自然邻接 | 是 |
| `docs/map/china_province_split_registry.csv` | 设计键、ID、RGB、母省和发展度登记 | 是 |
| `tools/map_pipeline/*_manual.json` | 审定后的像素数、连通块、邻接和沿海断言 | 是 |
| `history/provinces/*.txt` | 所有者、核心、文化、宗教、商品、发展度与设施 | 是 |
| `localisation_source/*.txt` | 可读的中文本地化源 | 是 |
| `map/definition.csv` 等完整覆盖文件 | 游戏实际读取的配套地图资产 | 由构建器生成 |
| `localisation/*.yml` | 游戏读取的编码本地化 | 由编码器生成 |
| `docs/map/previews/*report.json` | 构建与验证结果 | 由工具生成 |

设计文档记录“为什么这样做”，注册表记录“计划是什么”，正式模组文件记录
“游戏实际加载什么”。三者必须一致。

## 三、阶段 0：准备与基线锁定

### 3.1 确认游戏版本

地图工程必须锁定一个具体 EU4 版本，而不是只写 `1.37.*`。本项目当前基线为
EU4 1.37.5。

至少记录以下原版文件的 SHA-256：

- `map/provinces.bmp`
- `map/definition.csv`
- `map/default.map`
- `map/adjacencies.csv`

原版更新后哈希发生变化时，不应直接绕过检查。需要先重新审计省份 ID、底图和
特殊邻接，再决定是否迁移基线。

### 3.2 确认工作区安全

开始绘图前：

- 查看 `git status --short`；
- 确认哪些修改属于当前批次；
- 备份尚未提交的手绘 BMP；
- 不使用 `git reset --hard`、`git checkout --` 等命令清理手绘成果；
- 不直接修改 Steam 安装目录中的原版地图。

### 3.3 建立批次

为每个区域分配稳定批次键，例如 `B02`、`B03`。批次应满足：

- 地理上相邻；
- 可以单独审图；
- 共享的旧省份能在同一次重划中处理；
- 不会在尚未完成时暴露空 ID 给游戏。

## 四、阶段 1：冻结设计、ID 与 RGB

### 4.1 先填拆省总表

每个新省至少确定：

- 稳定设计键；
- 中文名、英文名、内部键；
- 数值母省与几何来源；
- 目标 Area；
- 推荐 1444 年所有者；
- 原母省发展度；
- 保留母省与新省发展度；
- 商品、文化、宗教和核心；
- 拆分理由与不确定性；
- 绘制批次。

### 4.2 ID 规则

- 新 ID 不得与原版或已实装省份冲突；
- 建议按批次连续分配，方便独立部署；
- `default.map` 的 `max_provinces` 必须等于“当前正式定义的最高省份 ID + 1”；
- 规划中的未来 ID 不得提前写入正式 `definition.csv`；
- 规划 ID 顺延时，禁止对全仓库做纯数字替换，因为相同数字可能是坐标、日期或
  其他数据。

### 4.3 RGB 规则

每个新省 RGB 必须：

- 三通道均为 `0–255` 整数；
- 不与原版、现有模组省份或其他规划省份重复；
- 在 `definition.csv`、注册表、审定配置和 BMP 中完全一致；
- 不使用近似色替代；
- 一经用于手绘，原则上永久冻结。

新增设计插入已有注册表时，应只迁移冲突的 ID，不应让仍未绘制省份的 RGB
整体重排。

### 4.4 注册表检查

本项目使用：

```sh
python3 tools/map_pipeline/allocate_registry.py \
  --vanilla-root "/path/to/Europa Universalis IV"
```

只有在明确进行 ID/RGB 登记迁移时才使用 `--write`。日常验证不得重写注册表。

## 五、阶段 2：手绘 `provinces.bmp`

### 5.1 文件格式

当前项目的正式 BMP 必须保持：

- 尺寸 `5632 × 2048`；
- RGB 真彩色；
- 24 位；
- 无压缩 `BI_RGB`；
- 经典 40 字节 DIB 头；
- 像素数据偏移 `54`；
- 不使用索引色、RLE 压缩、透明通道或抗锯齿。

部分绘图软件会保存成 Windows V4/V5 BMP。像素可能正确，但 EU4 兼容性更差。
正式交付前应无损转为经典 24 位 BMP，并逐像素确认转换前后完全相同。

### 5.2 绘图工具设置

- 使用铅笔或像素笔，不使用画笔；
- 硬度 100%，不透明度 100%；
- 关闭抗锯齿、羽化、颜色管理混合和自动平滑；
- 缩放时使用最近邻显示；
- 直接输入冻结 RGB，不依赖目测取色；
- 保存后重新打开，确认仍是 RGB 而非调色板模式。

### 5.3 边界质量

每个新省应满足：

- 主体为四向连通；
- 不依赖对角线连接；
- 没有无意的单像素飞地；
- 没有易断裂的单像素长颈；
- 存在足够大的实心点击核心；
- 与预期母省和外部省份保留合理公共边；
- 沿海省拥有明确海岸，内陆省不误触海区；
- 不切走旧省的城市、港口、奇观或其他锁定锚点。

岛屿和多连通块不是绝对禁止，但必须是有意设计，并在审定配置中记录每个连通块
的像素数。

### 5.4 跨母省重划

若手绘边界跨越多个原版母省：

1. 保存旧色到新色的像素来源统计；
2. 确认变化只发生在授权区域；
3. 重新计算所有受影响旧省的邻接和点位；
4. 在文档中明确“几何来源”和“发展度母省”的区别；
5. 废弃只支持单母省切割的旧自动生成方案。

## 六、阶段 3：几何审计

手绘完成后，先不要写历史或经济数据。应先回答以下问题：

### 6.1 基本检查

- BMP 尺寸、模式、位深和头格式是否正确；
- 是否出现未登记 RGB；
- 新省颜色是否真的存在；
- 每个新省有多少像素；
- 相对原版共有多少变化像素；
- 变化是否逃出允许的原版省份范围；
- 新旧省份各有几个四向连通块；
- 每个省的包围盒和主块面积是否足够点击。

### 6.2 邻接检查

EU4 的普通陆地和海岸邻接由 `provinces.bmp` 自动推导。审计应记录每个新省的：

- 全部四向邻接省份；
- 是否接触海区；
- 是否意外形成跨山脉捷径；
- 是否切断旧省之间原本应保留的通道；
- 是否出现只靠一个像素边连接的脆弱邻接。

只有海峡、运河等特殊通行关系才写入 `map/adjacencies.csv`。不要为普通接壤
手工添加特殊邻接。

### 6.3 冻结审定断言

通过审图后，把以下结果写入批次的 `*_manual.json`：

- ID、RGB 和英文定义名；
- 像素数；
- 连通块规模；
- 邻接白名单；
- 沿海属性；
- 需要检查点位的旧省与新省；
- 每个港口对应的海区；
- 相对原版的总变化像素；
- 允许发生变化的原版省份范围。

这些断言是防止以后误改地图的护栏，不是地图生成源。

## 七、阶段 4：更新全部联动资产

仅修改 `provinces.bmp` 不足以产生可玩省份。以下资产必须逐项处理。

### 7.1 `map/definition.csv`

为每个正式新省增加：

```text
ID;R;G;B;English Definition Name;x
```

检查：

- ID 唯一；
- RGB 唯一；
- 正式定义的新增 ID 恰好等于当前已绘制批次；
- 没有只在定义表存在、但 BMP 中没有像素的空省。

### 7.2 `map/default.map`

更新：

```text
max_provinces = 最高正式省份ID + 1
```

这是最常见的地图加载失败原因之一。

### 7.3 Area、Region 与 Superregion

- 每个陆地新省必须且只能属于一个 Area；
- 新 Area 必须加入正确 Region；
- Region 必须属于正确 Superregion；
- 若只向已有 Area 加省，Region 和 Superregion 可能无需修改，但仍要检查；
- Area 大小要兼顾治理成本、州界、诸侯边界和玩法，不只追求数量平均。

涉及文件：

- `map/area.txt`
- `map/region.txt`
- `map/superregion.txt`，仅在模组确实需要覆盖时

### 7.4 洲、气候与地形

逐省写入：

- `map/continent.txt`
- `map/climate.txt`
- `map/terrain.txt`

地形依据自然地理和玩法选择，不应机械继承现代土地利用。气候可以继承母省，
但必须检查热带、季风、严冬等可叠加类别。

### 7.5 贸易节点与贸易公司

每个新省必须加入正确贸易节点：

- `common/tradenodes/00_tradenodes.txt`

若该区域支持贸易公司，还要加入：

- `common/trade_companies/00_trade_companies.txt`

贸易节点归属缺失会导致省份贸易表现异常，即使地图本身能够加载。

### 7.6 `map/positions.txt`

每个省份通常包含七组位置，每组为 `x y`：

1. 城市；
2. 单位；
3. 省名文字；
4. 港口；
5. 辅助点；
6. 辅助点；
7. 预留点。

坐标系转换：

```text
Clausewitz x = BMP x
Clausewitz y = BMP高度 - BMP y
```

当前地图高度为 `2048`。

位置要求：

- 城市、单位、文字和辅助点必须落在所属省份颜色内；
- 内陆省的港口槽也放在本省陆地内；
- 沿海省的港口点必须落在正确海区；
- 港口海点必须与所属陆省至少有一条四向公共边；
- 手绘改变旧省边界后，必须复核旧省锚点，不能只给新省追加位置；
- 奇观位置通常跟随所属省份城市或界面资产，还要单独检查视觉效果。

### 7.7 省份历史

每个新省需要唯一的：

`history/provinces/ID - Name.txt`

至少包含：

- `owner`
- `controller`
- `add_core`
- `culture`
- `religion`
- `capital`
- `trade_goods`
- `base_tax`
- `base_production`
- `base_manpower`
- `is_city = yes`
- 发现组与必要的后续历史

如果从旧省拆出，旧省历史也必须同步回调，避免无意复制发展度。

### 7.8 本地化

每个新省至少提供：

```text
PROV<ID>:0 "省名"
PROV_ADJ<ID>:0 "省名"
```

本项目先编辑 UTF-8 可读源，再运行中文双字节编码器：

```sh
python3 tools/encode_eu4_chinese_localisation.py
python3 tools/encode_eu4_chinese_localisation.py --check
```

不要直接手改已经编码的 `.yml`。

### 7.9 硬编码省份引用

搜索旧省 ID 是否被以下内容引用：

- 奇观和省份修正；
- 任务、事件、决议；
- 触发修正；
- 国家首都与固定首都；
- 海峡和运河；
- 宗教中心；
- 贸易中心；
- 初始要塞；
- 特殊建筑；
- 书签和开局介绍。

必须明确哪些资产保留在旧省，哪些迁往新省。以广州为例，城市、主港、三级贸易
中心、南海神庙和贸易效率特性都被明确锁定在 667。

## 八、阶段 5：历史与游戏性数值

### 8.1 发展度以母省组核算

对每个拆分组分别计算：

```text
拆分后合计 = 保留母省 + 全部新省
变化量 = 拆分后合计 - 拆分前母省
```

税收、生产和人力必须分别核算，不能只比较总发展度。

默认原则是守恒。若每个已开发省必须至少为 `1/1/1`，确实无法守恒时，可以批准
最小增量，但必须：

- 在注册表记录 `group_dev_delta`；
- 在设计文档说明原因；
- 在验证器中显式写出批准的分项增量；
- 纳入全国发展度统计。

### 8.2 商品选择优先级

商品不应按现代 GDP 或当代知名产业决定。建议依次考虑：

1. 1444 年前后的地方生产与税源；
2. 传统农业、矿业、盐业、手工业和港口职能；
3. 架空世界线已经改变的贸易路线；
4. 与邻省商品的差异化；
5. 游戏平衡；
6. 玩家认知。

避免把近代才传入或产业化的作物直接放进 1444 年。

### 8.3 文化、核心与所有者分开判断

- 文化描述当地主要社会文化；
- 所有者描述 1444 年实际控制；
- 核心描述政治法理和潜在争端；
- 使用某种文化不自动意味着必须给对应国家核心；
- 争议核心会直接制造开局战争动机，应当有意识地控制数量。

### 8.4 特殊设施克制使用

一级贸易中心、要塞、特殊建筑和永久修正应有明确历史与玩法理由。低发展度不代表
没有战略价值；可以用要塞、港口或商路体现价值，而不是单纯堆发展度。

## 九、阶段 6：构建器设计

一个安全的正式构建器应当：

1. 校验原版基线哈希；
2. 以只读方式打开正式 `provinces.bmp`；
3. 校验 BMP 头、尺寸、模式和颜色；
4. 校验变化像素范围和审定省份像素数；
5. 从锁定原版生成完整覆盖文本文件；
6. 生成构建报告和输出哈希；
7. 明确报告“手绘几何未被修改”。

正式构建器中不得出现：

- 从旧多边形重新生成正式 BMP；
- 把 staging BMP 复制到模组；
- 为通过测试而自动修补手绘边界；
- 未经审图自动迁移城市或港口；
- 根据当前行号或文件顺序猜测省份 ID。

旧预览工具如果保留，输出路径必须限制在 `build/map/` 等一次性目录。

## 十、阶段 7：静态验证

静态验证至少覆盖：

- BMP 头、尺寸、位深和压缩；
- ID/RGB 唯一性；
- 正式新增 ID 集合；
- 总变化像素与允许变化范围；
- 像素数、连通块、邻接和沿海属性；
- 所有受影响省份的位置槽；
- 港口海区和四向贴岸；
- Area、Region、Superregion；
- Continent、Climate、Terrain；
- Trade Node、Trade Company；
- 省份历史、核心、商品和发展度；
- 母省组守恒或批准增量；
- 贸易中心、要塞和锁定奇观；
- 本地化键与编码；
- 构建报告中的文件哈希。

本项目 B01 命令：

```sh
python3 tools/map_pipeline/build_b01_mod.py \
  --vanilla-root "/path/to/Europa Universalis IV"

python3 tools/map_pipeline/validate_b01_mod.py \
  --vanilla-root "/path/to/Europa Universalis IV"

python3 tools/encode_eu4_chinese_localisation.py --check
```

### 10.1 幂等检查

正式构建器连续运行两次后，全部输出哈希应完全一致。若第二次仍改变文件，说明：

- 输出依赖时间或随机数；
- 生成顺序不稳定；
- 构建器重复追加成员；
- 报告包含非确定性字段；
- 第一次构建生成了第二次才会读取的状态。

任何一种情况都应在实机前修复。

### 10.2 Git 差异检查

至少运行：

```sh
git status --short
git diff --check
git diff --stat
```

确认：

- 没有误改原版安装目录；
- 没有提交临时截图、缓存或字节码；
- 没有无关用户文件；
- 二进制 BMP 大小和格式符合预期；
- 所有新增历史和本地化文件都已纳入差异。

## 十一、阶段 8：EU4 引擎实机验收

### 11.1 启动前

- 模组文件夹与 `.mod` 描述文件已安装；
- 启动器中只启用本模组及明确需要的依赖；
- 使用与基线一致的 EU4 版本；
- 记录启动前日志时间，避免把旧错误当作本轮错误。

### 11.2 必须使用新存档

地图定义发生变化后，旧存档不能作为可靠验证。应：

1. 启动 EU4；
2. 选择 1444 年书签；
3. 新建游戏；
4. 进入地图后暂停；
5. 必要时在控制台启用 `debug_mode` 查看省份 ID。

### 11.3 逐省检查

每个新省确认：

- 名称与 ID；
- 所有者、控制者和核心；
- 文化、宗教；
- 税收、生产、人力；
- 商品；
- 地形与气候表现；
- Area、Region 与贸易节点；
- 是否能稳定点击；
- 单位是否可以进入和离开；
- 与预期邻省是否能正常寻路；
- 沿海省是否显示港口；
- 船只是否能停靠；
- 贸易中心、要塞和奇观是否位于正确省份。

同时检查被切割的旧省，确认其城市、港口、贸易中心、要塞和奇观没有被新边界
偷走。

### 11.4 日志检查

退出游戏后检查本轮新写入的：

- `logs/error.log`
- `logs/setup.log`
- `logs/game.log`
- `logs/system.log`

优先搜索：

```text
province
definition
map
adjacency
position
terrain
area
trade
localisation
```

大型汉化模组可能产生大量既有日志噪声。判断问题时要比较启动时间、文件偏移和
本轮新增 ID，不能只看日志总行数。

### 11.5 保存与读取

最后：

1. 运行数日；
2. 保存新档；
3. 返回主菜单；
4. 重新读取；
5. 再次检查新省、军队、港口、要塞和贸易中心。

地图能进入不代表存档序列化一定正确。

## 十二、常见故障与定位

| 现象 | 优先检查 |
|---|---|
| 初始化地图时崩溃 | BMP 格式、未知 RGB、重复定义、`max_provinces` |
| 新省显示为异常色块 | 抗锯齿颜色、RGB 与 `definition.csv` 不一致 |
| 新省不存在 | BMP 无该色、ID 未进入正式定义、`max_provinces` 过小 |
| 省份无法点击 | 主块过小、细长、无实心核心、点位落错省 |
| 城市或单位模型跑到邻省 | `positions.txt` 陆地点没有随手绘边界迁移 |
| 港口不显示或朝向异常 | 港口点不在海区、不贴本省、海区 ID 错误 |
| 内陆省出现港口问题 | 内陆省第四位置槽落到了海区 |
| 省份没有州 | Area 缺失、重复或 Region 未包含新 Area |
| 贸易值异常 | 未加入贸易节点或贸易公司 |
| 地形或气候异常 | `terrain.txt`、`climate.txt` 成员错误或重复继承 |
| 发展度暴涨 | 只复制新省历史，没有回调母省 |
| 名称乱码或缺失 | 本地化键缺失、BOM 或中文编码流程错误 |
| 奇观或修正消失 | 旧省硬编码引用被新边界或 ID 迁移破坏 |
| 第二次构建继续产生差异 | 追加式生成、非确定性排序或时间字段 |
| 手绘地图被恢复成旧版 | 正式构建器仍在调用预览生成器或复制 staging BMP |

## 十三、每批完成定义

一个批次只有同时满足以下条件，才能标记为“正式实现”：

- 设计表、注册表与决策记录已更新；
- 手绘边界获得用户确认；
- 正式 BMP 格式正确；
- ID、RGB、像素、连通块和邻接通过；
- 全部联动资产已生成；
- 历史、商品与发展度通过审核；
- 构建连续运行两次无漂移；
- 静态验证报告通过；
- 新 1444 年游戏完成逐省检查；
- 日志没有新增阻断错误；
- 保存与读取成功；
- Git 差异只包含本批次预期文件。

若只通过静态验证，应明确写成“已正式接入并通过静态校验，待实机验证”，不能
简写成“已经完全完成”。

## 十四、向后续批次扩展

当前 `build_b01_mod.py` 和 `validate_b01_mod.py` 仍带有 B01 专用名称。B02 以后
不应复制八套逐渐分叉的脚本。推荐逐步重构为：

```text
批次 manifest
    ├── ID / RGB / 名称
    ├── 几何断言
    ├── Area / Region / Terrain / Climate
    ├── Trade Node / Trade Company
    ├── Position 与港口
    └── History 与发展度组
              ↓
通用只读构建器 + 通用验证器
              ↓
正式模组资产 + 批次报告
```

无论工具如何重构，`provinces.bmp` 的手绘权威地位、静态与实机双重验收，以及
发展度组核算原则都不改变。
